## Summary
Select an open-source Static Application Security Testing (SAST) tool, run it against a provided repository, evaluate the findings for accuracy (including false positive rate), and produce a clean, structured Excel report of confirmed true positives with remediation-relevant metadata.

## Background / Context
SAST tools are a core part of a mature AppSec program, but no tool is perfect — every scanner produces noise. A key skill for an AppSec engineer is not just running a tool, but critically evaluating its output: separating signal from noise, enriching findings with real-world risk context (CVSS, EPSS, KEV), and presenting results in a way developers can actually act on. This ticket simulates that end-to-end workflow.

## Acceptance Criteria
- [ ] An open-source SAST tool is selected and justified (see Task 1)
- [ ] Tool is successfully installed/downloaded and run against the provided target repo
- [ ] Raw scan output is saved and included as an artifact
- [ ] Each finding is manually triaged as **True Positive (TP)** or **False Positive (FP)**
- [ ] False positive ratio is calculated and documented with reasoning
- [ ] All confirmed true positives are compiled into a well-structured Excel workbook per the schema below
- [ ] A short written summary/evaluation of the tool is submitted alongside the report

### Task 3 — Manual Triage & Evaluation
- Review **every** finding generated by the scan (or a representative, clearly-documented sample if volume is very high — get instructor sign-off if sampling).
- For each finding, determine:
  - Is this a **true positive** (a real, exploitable or legitimate code quality/security issue)?
  - Is this a **false positive** (tool flagged something that isn't actually a valid issue in context)?
- Document your reasoning for at least a handful of representative FP and TP examples — don't just label them, explain *why*.
- Calculate the **False Positive Ratio**:

  ```
  FP Ratio = False Positives / Total Findings   (express as % as well)
  ```

  Also report:
  - Total findings
  - Total TP count
  - Total FP count
  - True Positive Rate (TP / Total)

## Excel Report — Required Column Schema

| Column | Description |
|---|---|
| **Finding ID** | Unique identifier (e.g., SAST-001) for traceability back to raw scan output |
| **Title** | Short, clear name of the vulnerability/finding |
| **Severity** | Tool-reported severity (Critical/High/Medium/Low/Info) — normalize if tool uses a different scale |
| **Description** | Plain-language explanation of the issue and why it matters |
| **File Path / Location** | File name + line number(s) where the issue was found |
| **CWE ID** | Relevant CWE classification (e.g., CWE-89 for SQL Injection) |
| **CVSS Score** | CVSS base score (v3.1 preferred) — calculate manually if tool doesn't provide one ([NVD CVSS Calculator](https://nvd.nist.gov/vuln-metrics/cvss/v3-calculator)) |
| **CVSS Vector** | Full vector string supporting the score |
| **EPSS Score** | Exploit Prediction Scoring System probability (lookup via [FIRST.org EPSS API](https://www.first.org/epss/)) — *if applicable* (mainly for known CVEs, e.g., in dependency findings) |
| **KEV Status** | Yes/No — check against CISA's [Known Exploited Vulnerabilities catalog](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) — *if applicable* |
| **Confidence** | Tool's confidence rating for the finding, if provided |
| **Remediation Guidance** | Concrete, actionable fix guidance for the developer (not generic — specific to the finding) |
| **References** | Links to CWE page, OWASP page, tool docs, or other supporting sources |
| **Status** | Triage status (e.g., "Confirmed - Needs Fix", "Confirmed - Accepted Risk") |
| **Notes** | Any additional analyst notes (e.g., exploitability caveats, business context) |

> **Note:** CVSS/EPSS/KEV mainly apply cleanly to CVE-based findings (e.g., vulnerable dependencies). For pure code-pattern SAST findings (like a hardcoded secret or SQLi pattern) without a CVE, mark these columns as **N/A** and rely on Severity + CWE + your own CVSS estimate instead. Explain this reasoning briefly in your summary.

### Formatting requirements for the Excel file
- Freeze the header row
- Use filters on all columns
- Color-code the **Severity** column (e.g., red = Critical, orange = High, yellow = Medium, green = Low)
- Sort by Severity (descending) by default
- Include a summary tab with: total findings scanned, TP count, FP count, FP ratio, tool name/version, repo scanned, date of scan
